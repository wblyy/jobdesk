# 实习推荐 · 接待后台

企微里人工接待时用的匹配工具。把候选人的简历放进来，它给出**今天该推的那一个岗位**，以及为这个岗位改写好的简历。

整个工具是一个静态网页：没有服务器，没有大模型调用，简历不离开你的电脑。

线上地址：**https://wblyy.github.io/jobdesk/**（手机浏览器也能开，收进书签随时用）

## 怎么用

1. 打开页面。
2. 把简历拖进第一栏，或者直接粘贴文字。支持 PDF / docx / txt / html。
3. 页面直接给出一个岗位：公司、岗位名、地点、出勤要求、薪资，以及**为什么是它**——JD 的哪句话，对上你简历的哪条经历。这一栏底下还有一行判定依据（档位 + 核心职责对上了几条），候选人问「为什么是这个」的时候照着念。
4. 点「复制推荐话术」，粘到企微发出去。这段文字是不带图片的纯文本，手机上一屏能读完。
5. 对方回「1」或「跟」以后，点「生成改好的简历」。左边是改好的简历正文，右边是改了哪几处、为什么改。两个都可以单独复制。
6. 不合适就点「换下一个岗位」。推过的公司会排到后面，第二天不会又推同一家。

## 时间

这里不追秒数。发给候选人的那句话是唯一要交的东西，所以慢一点换准确是划算的。

实测（330 个岗位、390px 手机模拟）：

- 打开到能操作：约 1.3 秒（含页面本身加载），其中前 120 个岗位建索引约 0.4 秒。剩下的在浏览器空档里补，页面不卡。
- 放进简历到出推荐：约 0.5 秒（冷启动 0.9 秒）。
- 点「生成改好的简历」：约 0.1 秒（冷启动 0.3 秒）。
- 第一次传 PDF 要下载解析组件（约 1.5 MB）。页面空闲时会提前下好，多数时候感觉不到这一步。

索引没补完就放进简历也能用：先按已有岗位匹配，剩下补完后会自动重算一次——前提是运营还停在第一个岗位卡片上。已经在读的推荐不会在脚下被换掉。

## 更换岗位库

右上角「更换数据」，选新的 xlsx。表格里需要有「岗位」「公司」「JD原文」三列，其余列（薪资、工作地点、实习安排、经验学历、招聘者与活跃）按原来的规则解析。

导入结果存在这台电脑的浏览器里，刷新不丢。点「恢复内置数据」回到随包附带的版本。

换一台电脑、或者清了浏览器数据，导入的版本就没了——重导一次即可。

## 自己的电脑上跑

浏览器直接打开 `index.html` 不行（`file://` 下模块和 fetch 会被拦）。起一个静态服务器：

```bash
python3 -m http.server 8099
# 打开 http://localhost:8099
```

## 更新岗位库（开发者）

把新的 Excel 转成随包的 JSON：

```bash
python3 -I tools/build_data.py ../../uploads/杭州互联网实习岗位-334.xlsx data.jobs.json
```

## 改匹配逻辑

| 文件 | 管什么 |
|---|---|
| `js/lexicon.js` | 概念词表。角色 / 技能 / 领域 / 方法 / 特质，每个概念带同义词和父级。**要调匹配精度，先改这里。** |
| `js/engine.js` | 解析、打分、找证据、改简历（P2 / P3 / P5 都在这里） |
| `js/verify.js` | 改稿自检（P6）。公司名、时间、数字、每条原经历是否还在 |
| `js/message.js` | 发给候选人的纯文本话术（P7） |
| `js/dataset.js` | 数据加载与 Excel 覆盖 |
| `js/parse.js` | PDF / docx / 文本提取 |

## 内部怎么走的（P2–P7）

和面试助手那套流程对齐，只是全部在浏览器里跑、不调模型：

- **P2 JD 拆解**：把 JD 切成硬门槛和加分项。带「必须 / 要求 / 至少 / 仅限」的算硬门槛，带「优先 / 加分 / 更佳」的算加分项。招聘批次、投递截止、毕业起止时间这类元信息不算要求，也不算证据。
- **P3 人岗匹配**：0–95 分，四个维度（硬门槛 40 / 职责 30 / 职能 20 / 加分 10），再过一遍降级链——方向不对的直接压到低档，硬门槛缺口明显但在主线上的一分不扣。产出档位：强匹配主投 / 良好值得投 / 够一够需重包装 / 偏弱 / 不匹配。
- **P5 改写**：命中句 → 优势牌 → 降维牌 → 经历（整段保留）→ 技能 → 荣誉。公司名、职位、起止时间只读，一个字不动；只增不减；不出现「我」；数字只能来自原简历。
- **P6 自检**：改稿生成后立刻机械核对一遍，结果显示在改动面板最上面。「自检通过」是说公司名、起止时间、数字、每条原经历都对得上，不是说改得好。没过就以红条挡在前面，别直接发。
- **P7 话术**：纯文本，13 行以内，每行不超过 32 字。公司名和日期照抄，不出现概率措辞（「大概率能」「基本稳」），并且**这段话不能原样发给另一个岗位**——JD 的职责句和你的经历都得是这条独有的。

## 卡片上那行「判定依据」

推荐卡底部有一行小字，比如「方向吻合，硬门槛没过」·「核心职责 2/2 条对得上」。这是给运营用的：候选人问「为什么是这个」，照着念就行。它和档位来自同一套 P3 判定，不另设阈值——两套阈值迟早对不上，运营看到「很对口」却在下面读到「缺关键硬门槛」，就不信这个工具了。

## 回归

```bash
node tools/test_engine.mjs
```

六份样例简历（产品、算法、设计、运营、游戏策划、后端）。每份都检查：P6 必须是 PASS，命中句必须落在具体经历上，引文不能切在英文词中间或括号里，话术不超过 14 行 / 34 字，不能出现概率措辞，两个不同岗位的话术不能一字不差。最后打印 `ALL FIXTURES PASS`，否则列出失败项并返回非零。

改完词表或引擎，先跑这个，再看一眼页面上的推荐卡——回滚只花一分钟。

## 几条不要改动的前提

**不编。** 改简历只做三件事：重排、收紧、把已有的内容提到前面。「主导」「从 0 到 1」这类词只在候选人自己写过的时候才出现——面试官第一个追问的就是这些词。

**「负责」可以删，「参与」「协助」「配合」不能删。** 前者是空转，后者是真实的角色边界。删掉「配合」等于把协助者写成主导者，而且常常把句子的主语一起删没了。

**分数不显示给候选人。** 后台里也只显示档位：强匹配，主投 / 良好，值得投 / 够一够，需重包装 / 偏弱，除非特别想去 / 不匹配。一个 82 分会引来「为什么不是 90」的争论，而档位说的是决策，不是评分。

**没有对应经历就说没有。** 有些岗位方向对、但 JD 里找不到一句能和简历对上的话。这时候话术会直说「只能算方向对，别把话说满」，而不是从行业词里凑一个理由出来。
